# Spec 模板（方案设计阶段产出）

`design` 阶段的产出。从当前上下文获取 `analysis` 阶段的分析结论，综合成 spec：前半是「要解决什么」（问题陈述 / 解决方案 / 用户故事 / 目标），后半是「怎么实现」（方案选型 / 设计方案 / 测试方案）。

通篇使用 `CONTEXT.md` 中的领域术语，并尊重该领域已有的 ADR。

硬规则：

- **不要写具体文件路径和代码片段**——它们很快就会过时
- 例外：如果某个片段能比散文更精确地编码一个决策（状态机、reducer、schema、类型形状），把富含决策的部分内联进来，并注明来源。剪到只留决策相关的部分，不要留能跑的 demo

```md
## 问题陈述

要解决什么问题，以及为什么要解决该问题。

## 解决方案

从用户角度描述诉求：用户想要什么、解决之后是什么样子。只讲「要解决什么」，不涉及怎么实现。

## 用户故事

**用户与系统的一次交互（一次会话）就是一个用户故事。同一次交互中的多个步骤属于同一个用户故事，不要拆到不同的故事里。**

每个故事按下面的格式写：

### US-N：<故事标题>

- **角色**：谁在与系统交互
- **目标**：这次交互想达成什么
- **成功标准**：怎样算这次交互成功

**交互步骤**：

1. 用户 …
2. 系统 …
3. 用户 …
4. 系统 …

**边界与异常**：

- <这次交互中可能出岔子的地方，以及期望的系统反应>

---

## 目标

### 范围

本次要覆盖的边界：涉及哪些上下文、哪些流程、哪些用户群；边界止于何处。

### 功能性目标

1. <系统必须能做的事>
2. <系统必须能做的事>

### 非功能性目标

1. <性能 / 可靠性 / 安全 / 可维护性 / 合规等方面的约束，尽量可度量>

### 非目标

明确排除在本次之外的事情，以及为什么推迟。

## 方案选型

本次考虑过的方案，以及最终为什么选这一个。

- **A 最小改动**：<一句话概括> —— <为什么选 / 为什么不选>
- **B 最干净彻底的架构**：<一句话概括> —— <为什么选 / 为什么不选>
- **C 务实折中**：<一句话概括> —— <为什么选 / 为什么不选>
- **选定**：<A / B / C / 混合方案>。<选定的理由，以及为此接受了什么代价>

## 设计方案

### 领域模型

本次涉及的实体、值对象、聚合、领域事件，以及它们之间的关系。

术语必须来自 `CONTEXT.md`；本阶段新引入的术语要回头补进 `CONTEXT.md`。

### 物理模型

领域模型落地成什么结构：表结构与索引、消息格式、API payload、文件布局等。

### 模块变更

#### 新建

- <模块名>：<职责，以及它为什么值得独立成模块>

#### 修改

- <模块名>：<改什么，为什么必须改>

（写模块名，**不写**具体文件路径）

### 模块交互时序

逐个用户故事（或逐个关键交互）描述：参与者有哪些，消息怎么流动。

### 模块接口与契约

每个接口写明：

- 签名
- 不变式
- 顺序约束
- 错误模式
- 性能特征

## 测试方案

### 测试范围

测哪些模块与接口，以及**不测**什么。

### 测试用例

逐条列出：前置条件、操作、期望的可观察结果。只断言透过接口的外部行为，不断言内部状态。

### 需要 mock 的 seam

| seam | 依赖类别 | 为什么必须 mock | 适配器 |
| --- | --- | --- | --- |
| <seam 名> | 进程内 / 本地可替换 / 远程但自有 / 真正的外部服务 | <理由> | 生产用 X，测试用 Y |

**seam 纪律**：一个适配器意味着假想的 seam，两个适配器才是真的 seam。seam 越少越好，理想数量是一个。
```
