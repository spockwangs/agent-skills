# 设计方案模板

`design` 阶段的产出。基于 `analysis` 阶段的 spec（问题陈述 / 需求分析 / 用户故事），把领域模型和用户故事落成可实现的设计。

通篇使用 `CONTEXT.md` 中的领域术语，并尊重该领域已有的 ADR。

硬规则：

- **不要写具体文件路径和代码片段**——它们很快就会过时
- 例外：如果某个片段能比散文更精确地编码一个决策（状态机、reducer、schema、类型形状），把富含决策的部分内联进来，并注明来源。剪到只留决策相关的部分，不要留能跑的 demo

```md
## 方案选型

本次考虑过的方案，以及最终为什么选这一个。

- **A 最小改动**：<一句话概括> —— <为什么选 / 为什么不选>
- **B 最干净彻底的架构**：<一句话概括> —— <为什么选 / 为什么不选>
- **C 务实折中**：<一句话概括> —— <为什么选 / 为什么不选>
- **选定**：<A / B / C / 混合方案>。<选定的理由，以及为此接受了什么代价>

## 设计方案

### 领域模型

本次涉及的实体、值对象、聚合、领域事件，以及它们之间的关系。

术语必须来自 `CONTEXT.md`；本阶段新引入的术语要回头补进 `CONTEXT.md`。

### 物理模型 Schema

领域模型落地成什么结构：表结构与索引、消息格式、API payload、文件布局等。

### 模块变更

#### 新建

- <模块名>：<职责，以及它为什么值得独立成模块>

#### 修改

- <模块名>：<改什么，为什么必须改>

（写模块名，**不写**具体文件路径）

### 模块交互时序

逐个用户故事（或逐个关键交互）描述：参与者有哪些，消息怎么流动。

### 模块接口与契约

每个接口写明：

- 签名
- 不变式
- 顺序约束
- 错误模式
- 性能特征

## 测试方案

### 测试范围

测哪些模块与接口，以及**不测**什么。

### 测试用例

逐条列出：前置条件、操作、期望的可观察结果。只断言透过接口的外部行为，不断言内部状态。

### 需要 mock 的 seam

| seam | 依赖类别 | 为什么必须 mock | 适配器 |
| --- | --- | --- | --- |
| <seam 名> | 进程内 / 本地可替换 / 远程但自有 / 真正的外部服务 | <理由> | 生产用 X，测试用 Y |

**seam 纪律**：一个适配器意味着假想的 seam，两个适配器才是真的 seam。seam 越少越好，理想数量是一个。
```
