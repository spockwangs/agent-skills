从当前上下文获取需求分析阶段的分析结论（问题陈述 / 需求分析 / 用户故事），**不访谈，只综合已经讨论清楚的内容**，编写 spec；再理解当前代码，在 spec 之上输出方案设计。

## 流程

### 1. 从上下文编写 spec 前置部分

从当前对话上下文获取需求分析阶段的分析结论，**不访谈，只综合已经讨论清楚的内容**，按 [spec 模板](./references/spec-format.md) 写出 spec 的前置部分：

- **问题陈述**：要解决什么问题，以及为什么要解决它
- **解决方案**：从用户角度描述诉求（用户想要什么、解决后是什么样子）
- **用户故事**：一次交互（一次会话）就是一个用户故事；同一次交互的多个步骤属于同一个故事
- **目标**：范围、功能性目标、非功能性目标、非目标

通篇使用 `CONTEXT.md` 中的领域术语，并尊重该领域已有的 ADR。这部分是 spec 的「要解决什么」层面，不涉及怎么实现。把它展示给用户确认后，再进入第 2 步。

### 2. 框定问题空间

启动子 Agent 之前，先写一段面向用户的问题空间说明：

- 任何方案都必须满足的**约束**
- 方案要依赖的**依赖**及其类别（见下方「依赖类别」）
- 一段粗略的示意性代码草稿，用于把约束讲具体——**不是提案**，只是让约束可感

把它展示给用户，然后**立刻**进入第 3 步。用户阅读思考的同时，子 Agent 并行工作。

### 3. 并行启动 3 个子 Agent

同时启动 3 个子 Agent，**每个必须给出截然不同的方案**。给每个 Agent 一份独立的技术简报（涉及的模块、耦合情况、依赖类别、seam 后面是什么），并施加不同的设计约束：

| 子 Agent                | 设计约束                                                     | 它该优化什么                  |
|-------------------------|--------------------------------------------------------------|-------------------------------|
| **A：最小改动**         | 改动面最小；复用现有结构与 seam；不引入新抽象                | 风险最低、diff 最小、最快落地 |
| **B：最干净彻底的架构** | 忽略迁移成本，追求最深的模块、最干净的 seam 放置             | 长期可维护性、概念完整性      |
| **C：务实折中**         | 在 A 与 B 之间取平衡；允许有限重构，但每处重构都要有明确收益 | 投入产出比、可增量落地        |

简报中要同时带上**架构术语**（模块 / 接口 / seam / 适配器 / 深度 / 局部性）和**领域术语**（来自 `CONTEXT.md`），让三个 Agent 用同一套语言命名事物，否则后面没法对比。

每个子 Agent 输出（与[spec 模板](./references/spec-format.md)的章节一一对应，便于后续对比）：

1. **领域模型与物理模型 Schema**：实体 / 值对象 / 关系，以及落地的存储、消息、API 结构
2. **模块变更**：新增/修改哪些模块（写模块名，**不写**具体文件路径），各自为什么
3. **模块交互时序**：关键交互的参与者与消息流
4. **接口与契约**：签名、不变式、顺序约束、错误模式、性能特征
5. **依赖策略与适配器**：每处依赖属于哪个类别，怎么在 seam 上处理
6. **迁移路径**：从现状到该方案怎么走，能否增量落地
7. **权衡**：优势在哪、代价在哪，**什么情况下这个方案是错的**
8. **测试策略**：在什么 seam 上测，需要 mock 哪些 seam

### 4. 汇总对比，由用户选择

把三个方案**依次**呈现给用户（逐个展示，便于吸收），然后用一段文字横向对比。对比维度：

- **深度（depth）**：接口后面的行为杠杆——调用方每学一单位接口能撬动多少能力
- **局部性（locality）**：变更、缺陷、知识是集中在一处，还是散落到各个调用方
- **seam 放置**：接口开在哪一层，是否复用现有 seam，数量多少
- **改动面与风险**：要动多少东西，能否增量落地，回滚难度
- **与既有 ADR 的一致性**：是尊重已记录的决策，还是要求推翻它们

对比之后**给出你自己的推荐**：你认为哪个方案最强、为什么。如果不同方案的元素能组合得更好，提出一个混合方案。**要有主见**——用户要的是一个强判断，不是一份菜单。

然后让用户选择：A / B / C / 你推荐的混合方案。**在用户选定之前，不要往下走。**

### 5. 确定测试 seam

基于用户选定的方案，画出你打算在哪些 seam 上测试这个功能：

- **优先复用现有 seam**，而不是新开
- **尽可能用最高层的 seam**
- 必须新开 seam 时，在你能做到的最高点提出
- **跨代码库的 seam 越少越好，理想数量是一个**

就这些 seam 与用户确认是否符合预期。

### 6. 用领域术语输出 spec

按 [spec 模板](./references/spec-format.md) 写出最终 spec。第 1 步已写好前置部分（问题陈述 / 解决方案 / 用户故事 / 目标），本步在其后补上设计部分。**通篇使用项目的领域术语**（来自 `CONTEXT.md`），并尊重该领域已有的 ADR。设计部分产出 3 部分：

- **方案选型**：对比三个方案，说明每个方案的优势、代价、适用场景，以及最终为什么选这一个
- **设计方案**：领域模型与物理模型 Schema、模块变更、模块交互时序、模块接口与契约
- **测试方案**：测试范围、测试用例、需要 mock 的 seam

把完整 spec 发布到当前项目的 issue tracker（不知道 issue tracker 先询问用户）。

**不要写具体文件路径和代码片段**——它们很快就会过时。例外：如果某个草稿片段能比散文更精确地编码一个决策（状态机、reducer、schema、类型形状），把富含决策的部分内联进来，并注明来源。剪到只留决策相关的部分，不要留能跑的 demo。

这份 spec 就是下一步实现的输入。

## 依赖类别

依赖的类别决定了深度模块如何跨其 seam 进行测试：

1. **进程内**：纯计算、内存状态、无 I/O。可以直接合并模块，直接透过新接口测试，不需要适配器。
2. **本地可替换**：有本地测试替身的依赖（PGLite 之于 Postgres、内存文件系统）。用替身在测试套件里跑，seam 在模块内部，不在外部接口上。
3. **远程但自有**：你自己的跨网络服务（微服务、内部 API）。在 seam 上定义 port，模块拥有逻辑，传输作为**适配器**注入；测试用内存适配器，生产用 HTTP/gRPC/队列适配器。
4. **真正的外部服务**：不受你控制的第三方（Stripe、Twilio 等）。把外部依赖作为注入的 port，测试提供 mock 适配器。

**seam 纪律**：*一个适配器意味着假想的 seam，两个适配器才是真的 seam。* 除非至少两个适配器是合理的（通常是生产 + 测试），否则不要引入 seam——单适配器的 seam 只是间接层。

## 术语

对比方案时统一使用这套词汇，不要替换成「组件」「服务」「API」「边界」：

- **模块（module）**：有接口和实现的任何东西，与规模无关——函数、类、包、跨层切片
- **接口（interface）**：调用方为了正确使用模块必须知道的一切——类型签名，也包括不变式、顺序约束、错误模式、性能特征
- **seam**：可以在不改动该处代码的前提下改变行为的位置；即模块接口所在的位置
- **适配器（adapter）**：在 seam 上满足某个接口的具体实现，描述的是**角色**，不是内容
- **深度（depth）**：小接口后面藏大量行为 = 深；接口几乎和实现一样复杂 = 浅
- **杠杆（leverage）**：调用方从深度得到的东西——每学一单位接口获得更多能力
- **局部性（locality）**：维护者从深度得到的东西——变更、缺陷、知识、验证集中在一处，修一次到处生效
