# Spec 模板（需求分析阶段产出）

分析阶段结束时按此模板输出 spec。它只回答**要解决什么问题和为什么**，不涉及怎么实现——那是 `design` 阶段的活。

通篇使用 `CONTEXT.md` 中的领域术语。

```md
## 问题陈述

要解决什么问题，以及为什么要解决该问题。

## 需求分析

### 范围

本次要覆盖的边界：涉及哪些上下文、哪些流程、哪些用户群；边界止于何处。

### 目标

要解决到什么程度，以及怎样算解决了。

### 功能性目标

1. <系统必须能做的事>
2. <系统必须能做的事>

### 非功能性目标

1. <性能 / 可靠性 / 安全 / 可维护性 / 合规等方面的约束，尽量可度量>

### 非目标

明确排除在本次之外的事情，以及为什么推迟。

## 用户故事

**用户与系统的一次交互（一次会话）就是一个用户故事。同一次交互中的多个步骤属于同一个用户故事，不要拆到不同的故事里。**

每个故事按下面的格式写：

### US-N：<故事标题>

- **角色**：谁在与系统交互
- **目标**：这次交互想达成什么
- **成功标准**：怎样算这次交互成功

**交互步骤**：

1. 用户 …
2. 系统 …
3. 用户 …
4. 系统 …

**边界与异常**：

- <这次交互中可能出岔子的地方，以及期望的系统反应>

---

<用户故事示例>
### US-1：客户查看账户余额

- **角色**：手机银行客户
- **目标**：看到自己名下各账户的当前余额
- **成功标准**：所有账户余额在 2 秒内展示完毕，且金额与账本一致

**交互步骤**：

1. 客户打开 App 首页
2. 系统展示该客户名下的所有账户及其当前余额
3. 客户点选某个账户
4. 系统展示该账户的余额构成与最近交易

**边界与异常**：

- 客户名下无账户：展示空状态与开户引导
- 某个账户被冻结：余额照常展示，但标注冻结状态
- 余额服务不可用：展示上次成功获取的余额与时间戳

注意：步骤 3-4 与步骤 1-2 属于同一次会话，因此它们是 **US-1 内部的步骤**，不是 US-2。
</用户故事示例>
```
