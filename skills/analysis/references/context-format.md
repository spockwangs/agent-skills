# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一到两句话，描述这个上下文是什么、为什么存在。}

## 语言

**订单**：
{一到两句话的术语定义}
_避免_：购买、交易

**发票**：
交付后发给客户的付款请求。
_避免_：账单、付款请求

**客户**：
下订单的个人或组织。
_避免_：客户方、买家、账户
```

## 规则

- **要有主见。** 当多个词指同一概念时，挑最好的那个，把其余列在 `_避免_` 下。
- **定义要紧凑。** 最多一到两句话。定义它**是什么**，而不是它做什么。
- **只收录本项目上下文特有的术语。** 通用编程概念（超时、错误类型、工具模式）不属于这里，即使项目大量使用它们。添加一个术语前先问：这是这个上下文独有的概念，还是通用编程概念？只有前者才属于这里。
- **当自然聚类出现时，用小标题分组术语。** 如果所有术语都属于同一个内聚领域，平铺列表即可。

## 单上下文 vs 多上下文仓库

**单上下文（大多数仓库）：** 仓库根目录一个 `CONTEXT.md`。

**多上下文：** 根目录一个 `CONTEXT-MAP.md`，列出上下文、它们的位置，以及彼此的关系：

```md
# 上下文地图

## 上下文

- [下单](./src/ordering/CONTEXT.md)：接收并跟踪客户订单
- [账单](./src/billing/CONTEXT.md)：生成发票并处理支付
- [履约](./src/fulfillment/CONTEXT.md)：管理仓库拣货与发货

## 关系

- **下单 → 履约**：下单发出 `OrderPlaced` 事件；履约消费它开始拣货
- **履约 → 账单**：履约发出 `ShipmentDispatched` 事件；账单消费它生成发票
- **下单 ↔ 账单**：共享 `CustomerId` 和 `Money` 类型
```

本技能推断适用哪种结构：

- 如果 `CONTEXT-MAP.md` 存在，读取它以找到上下文
- 如果只有根目录 `CONTEXT.md`，则是单上下文
- 如果两者都没有，在第一个术语被确定时惰性创建根 `CONTEXT.md`

当存在多个上下文时，推断当前话题属于哪个上下文。如果无法确定，询问。
