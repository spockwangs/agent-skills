# ADR 格式

ADR 放在 `docs/adr/` 下，使用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

只有在需要第一个 ADR 时才惰性创建 `docs/adr/` 目录。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么、我们决定了什么、为什么。}
```

就这些。一个 ADR 可以只是一段话。价值在于记录"做了某个决策"以及"为什么"，而不是填满各个小节。

## 可选小节

只有在它们真正有价值时才加。大多数 ADR 不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在决策被重新审视时有用
- **Considered Options**：只有被否决的备选方案值得记住时才写
- **Consequences**：只有需要点明非显而易见的下游影响时才写

## 编号

扫描 `docs/adr/`，找到现有最大编号，加一。

## 何时提议写 ADR

以下三条必须同时成立：

1. **难以逆转**：以后改变主意的代价是显著的
2. **脱离上下文会令人费解**：未来的读者看到代码会想"他们到底为什么这么做？"
3. **是真实权衡的结果**：确实存在其他备选方案，而你出于具体原因选了其中一个

如果一个决策很容易逆转，跳过它：你反正会直接逆转。如果它不令人费解，没人会好奇为什么。如果不存在真正的备选方案，除了"我们做了显而易见的事"之外也没啥可记录的。

### 什么够格

- **架构形态。** "我们用 monorepo。""写模型是事件溯源，读模型投影进 Postgres。"
- **上下文之间的集成模式。** "下单和账单通过领域事件通信，而不是同步 HTTP。"
- **带锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都要：只是那些换掉要花一个季度的。
- **边界与范围决策。** "客户数据由客户上下文拥有；其他上下文只按 ID 引用。" 显式的"不"和显式的"是"一样有价值。
- **对显而易见路径的有意偏离。** "我们用手写 SQL 而不是 ORM，因为 X。" 任何合理读者会假设相反做法的地方。这些能阻止下一位工程师"修复"一个有意为之的东西。
- **代码里看不见的约束。** "因为合规要求，我们不能用 AWS。""因为合作伙伴 API 契约，响应时间必须低于 200ms。"
- **否决并不显然时的备选方案。** 如果你考虑过 GraphQL 却因为微妙原因选了 REST，记录下来；否则半年后有人会再次提议 GraphQL。
