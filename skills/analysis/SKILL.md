# 需求分析（Analysis）

在**需求分析阶段**，通过与用户反复、彻底的访谈逐步达成共识，把模糊的需求打磨成清晰的分析结论；与此同时，主动构建和打磨项目的领域模型，把术语写进 `CONTEXT.md`、把关键决策写进 ADR。

## 本技能的范围

本技能只做一件事：**把模糊的需求变成清晰、可共享的分析结论**。

- **属于本阶段**：澄清需求、划定边界、统一术语、暴露并消解被默默假设的东西、记录关键决策
- **不属于本阶段**：设计具体方案、技术选型、写实现计划、动手写代码

当分析结论达成后，**下一步才是基于该结论设计方案**——那是另一个阶段，不在本技能范围内。不要在本阶段越界给出实现方案。

（仅"阅读 `CONTEXT.md` 查术语"不是本技能——那是任何技能都能做的一行习惯。本技能用于当你正在澄清需求、改变领域模型、做出需求决策时。）

## 核心方法：分析树 + 轮次 + 前沿

把你和用户正在打磨的需求画成一棵**分析树**：每个决策分叉出挂在它之下的、更细的决策。

按**轮次**推进这棵树。**前沿（frontier）** 是所有「前置决策已经确定」的决策——也就是你现在就能问、而不必猜测尚未听到的答案的那些问题。每一轮把整个前沿一次性问出来：给每个问题编号，并给出你的推荐答案。等用户回答完，再进入下一轮。

每轮的格式如下：

```
❓ **Q1** — **<问题标题>**：<问题正文，可能是多段，包含多个选项>

➡️ <你的推荐答案>

---

❓ **Q2** — **<问题标题>**：<问题正文，可能是多段，包含多个选项>

➡️ <你的推荐答案>
```

每一轮用户的回答都会重塑这棵树：已确定的决策把前沿向外推，解锁依赖它们的那些问题。重新计算前沿，再问下一轮。一个答案若依赖于本轮尚未回答的另一个问题，那么这个问题属于**后面**的轮次，而不是本轮。

## 事实 vs 决策的分工

- **事实**是你的活，永远不是用户的。当前沿问题需要一个来自环境的事实（文件系统、工具、代码库等）时，派一个子 Agent 去找；不要问用户任何你自己能查到的东西。
- 不要因此卡住：一个正在进行的探查只是一个未确定的前置条件，所以只有依赖它的下游问题才需要等子 Agent 回报；先问前沿里的其余问题。
- **决策**是用户的：把每一个决策摆到用户面前，然后等待。

## 领域建模纪律

在访谈推进需求的同时，主动打磨领域模型。这是"主动"的纪律：挑战术语、发明边界场景、在术语和决策结晶的那一刻立刻把它们写下来。

### 对照术语表挑战

当用户使用一个与 `CONTEXT.md` 现有语言冲突的术语时，立刻指出。"你的术语表把'取消'定义为 X，但你似乎指的是 Y。到底是哪个？"

### 打磨模糊语言

当用户使用含糊或多义的词时，提出一个精确的规范术语。"你说的'账户'：是指客户还是用户？这是两个不同的东西。"

### 讨论具体场景

在讨论领域关系时，用具体场景去压力测试它们。发明能探测边界情况、迫使用户精确说出概念之间边界的情景。

### 与代码交叉验证

当用户陈述某物如何工作时，去查代码是否一致。如果发现矛盾，摆到台面上："你的代码取消的是整个订单，但你刚才说可以部分取消。到底哪个对？"

### 即时更新 CONTEXT.md

当一个术语被确定时，当场更新 `CONTEXT.md`，不要攒着批量写：一旦结晶就立刻记录。格式见 [references/context-format.md](./references/context-format.md)。

`CONTEXT.md` 应当完全不包含实现细节。不要把它当作规格说明、草稿纸或实现决策的仓库。它只是术语表，仅此而已。

### 克制地写 ADR

只有同时满足以下三条时才提议创建 ADR：

1. **难以逆转**：以后改变主意的代价是显著的
2. **脱离上下文会令人费解**：未来的读者会想"他们为什么这么做？"
3. **是真实权衡的结果**：确实存在其他备选方案，而你出于具体原因选了其中一个

三条缺任意一条就跳过 ADR。格式见 [references/adr-format.md](./references/adr-format.md)。

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明仓库有多个上下文，它指向每个上下文的位置。

惰性创建文件：只有当有东西要写时才创建。如果没有 `CONTEXT.md`，在第一个术语被确定时创建它；如果没有 `docs/adr/`，在第一个 ADR 需要时创建它。

## 完成标准

当**前沿为空**时，本次分析结束：分析树的每个分支都被走到，没有仍然被默默假设的东西。此时在对话中陈述分析结论。在用户确认你们已达成共识之前，不要进入下一阶段，也不要动手去实现。
