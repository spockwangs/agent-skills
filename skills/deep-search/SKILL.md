# 深度搜索（Searcher / Fetcher / Verifier 流水线）

对开放式、需要多方向同时探索、单轮搜索回答不了的研究问题，采用「主 agent 编排 + 三类子
代理流水线」：

1. **Searcher** 按角度搜集 URL；2. **Fetcher** 按 URL 提取可证伪论点；3. **Verifier**
对每条论点做对抗验证。主 agent 只做编排、去重、机械汇总，三类子代理之间**一律以文件路
径交互**，不在消息里回传文件内容。

**先判断是否需要本流程**：简单事实查询（一轮网页搜索即可回答）直接搜索作答，不走本
流程。本流程 token 消耗远高于普通问答，只用于高价值、信息量大的研究问题。

## 会话目录

每次执行开始时用 `mktemp -d` 创建一个会话临时目录，所有中间结果都放这里（只在本次执行
期间有效，无需跨会话保留）：

```text
$(mktemp -d)/
├── searcher-1.json    # Searcher 1：结果数组（url + tool，按相关性降序）
├── searcher-2.json    # Searcher 2：结果数组
├── fetcher-1.json     # Fetcher 1：论点数组（claim + sources）
├── fetcher-2.json     # Fetcher 2：论点数组
├── claims.json        # 主 agent 合并的全部论点（去重前）
├── dedup-claims.json  # 主 agent 语义去重后的论点（Top 20，sources 已并集）
├── verifier-1.json    # Verifier 1：验证结果（claim/evidence/sources/confidence）
├── verifier.json      # 主 agent 汇总：全部验证结果（含 low，第 5 步再筛选）
└── report.md          # 最终带引用报告
```

主 agent 与子代理之间只传**文件路径**；子代理的产出写入自己的文件后，只返回文件路径给
主 agent。

## 执行流程

### 第 1 步：宽检索侦察，理解问题并分解为多个角度

1. 复述对问题的理解，识别歧义点（研究对象指代、时间/版本/地域范围、研究深度），存在影
   响研究方向的歧义时一次性列出让用户澄清，直到用户确认理解。
2. **宽检索侦察（分解角度之前，主 agent 直接执行，不派子代理）**：用 3–5 个宽泛检索词
   摸一遍信息地形（包括内部与外部信源）。目的有三：
   - **发现专名**：扫出研究领域内的平台/系统/框架专名（如内部调研时的平台名），把它们
     作为关键词注入对应角度——专名是最强的检索词，通名检索（"MCP"/"agent"这类概念词）
     的相关性排序几乎永远挤不进专名自己的文档簇，不做这一步就会漏掉整个子系统；
   - **校准角度**：先看实际信息地形再分解，避免带着预设立场画地图；
   - **识别同簇文档**：提前观察哪些主题文档扎堆，为第 3 步簇配额提供依据。
   侦察结果片段（每次约 10 条摘要）允许进入主上下文（合计约 2–3k token，成本远低于角
   度分解错误的返工）；发现的专名与范围线索也可作为向用户澄清的输入材料（如"内部扫到
   X/Y 等平台，是否纳入调研范围？"）。
3. 把问题分解为多个**彼此正交的角度**（不同侧面 / 阵营观点 / 时间段 / 维度）。角度重叠
   会导致多个 Searcher 搜到相同内容——这是最常见的失败模式。角度数即 Searcher 数。分
   解时结合侦察结果：发现的专名归属到相关角度的关键词里，明显缺文档支撑的方向不强
   行设角度。
4. 为每个角度提炼 2–5 个检索关键词（含侦察发现的专名），供 Searcher 检索。

### 第 2 步：并行派发 Searcher 搜集 URL

1. **每个角度启动 1 个 Searcher**，所有 Searcher 的 Task 调用放在同一条回复里一次性发
   出，并发执行；逐个发起会退化为串行，耗时翻数倍。
2. 每个 Searcher 的 prompt 按 `references/searcher_prompt.md` 模板填写，传递：角度、关
   键词、调用预算、其输出文件路径（`<会话目录>/searcher-<n>.json`）。Searcher 的输出为
   `{url, tool}` 数组——tool 是发现该 URL 所用的搜索工具名（当前环境里实际调用的那个），
   下游 Fetcher 把它当作抓取线索，再按 URL 类型自行选择能读到该来源的工具。
3. 收集：每个 Searcher 只返回其输出文件路径，主 agent 机械记录，不读 URL 内容。

### 第 3 步：URL 去重、按复杂度分档配额筛选，并行派发 Fetcher

1. 主 agent 读所有 `searcher-<n>.json`，把 URL 合并去重（URL 级去重只挡同一链接，挡不
   住"不同链接、相同内容"，那类重复留给第 4 步论点去重处理）。
2. **按研究复杂度分档确定 URL 配额**（配额是 token 预算控制手段，不是质量机制）：
   - 简单问题（单一事实/方案，1–2 个角度）：**Top 6**
   - 中等问题（多维度对比，3 个角度左右）：**Top 10**
   - 复杂问题（多阵营/多子系统/需要交叉印证，4+ 角度）：**Top 15**
   依据第 1 步分解出的角度数定档；用户声明了优先级或范围的，以用户为准。
3. **排序规则（在配额内筛选）**，按以下优先级依次适用：
   a. **来源权威性优先**：官方文档/一手来源 > 代码仓库 > 权威媒体/技术博客 > 二手转载/
      论坛水帖。内部研究场景（内网文档/知识库/代码托管等）优先于公网来源——内部框架/
      系统的资料以内部为准，公网只作通用模式补充。
   b. **按 Searcher 轮转分配**：相关性只在同一 Searcher 内部可比（不同 Searcher 按各自
      角度评分，跨 Searcher 直接比大小无意义），故按角度轮转取额，保证每个角度都有代
      表进入，不因某角度"全局相关性低"被整体挤出。
   c. **同簇配额**：同一主题簇（同一文档的内部版/对外版、同一项目的仓库与教程、同域名
      同项目页）**最多保留 2 个**，超出的名额由该 Searcher 的下一个候选递补；簇内取舍
      按权威性（一手 > 二手）。同簇被裁剪的 URL 不派 Fetcher，但可作为论点的佐证引用
      保留在 sources 里。
   d. **来源类型多样性**：并列时优先让文档/代码/文章混排，避免全是同类来源。
4. 被配额裁剪的 URL 记录个数（及被同簇裁剪的代表簇名），写入报告「待进一步研究的论
   点」部分。
5. **每个入选 URL 启动 1 个 Fetcher**，所有 Fetcher 的 Task 调用放在同一条回复里一次性
   发出，并发执行。
6. 每个 Fetcher 的 prompt 按 `references/fetcher_prompt.md` 模板填写，传递：总问题、该
   URL、**该 URL 对应的读取工具提示（来自 searcher-<n>.json 的 tool 字段）**、其输出文
   件路径（`<会话目录>/fetcher-<n>.json`）。Fetcher 在当前可用工具中选择能实际读到该
   URL 的抓取方式（通用网页抓取通常读不到需鉴权的内部来源）；tool 字段只是线索，以
   URL 类型为准。
7. 收集：每个 Fetcher 只返回其输出文件路径。

### 第 4 步：论点语义去重合并，取 Top 20，并行派发 Verifier 对抗验证

1. 主 agent 读所有 `fetcher-<n>.json`，把全部论点合并为 `claims.json`（每条含 claim 与
   sources，可附带来源 fetcher 编号）。
2. **语义去重合并（派发 Verifier 之前）**：多条表达同一意思的论点合并为一条——claim 取
   表述最完整/信息量最大的一条（可融合各条互补细节），**sources 取并集**，并记录
   `corroborated_by`（合并前有几条独立论点、来自几个不同 fetcher）。同一主题文档（同一
   文档的内部版/对外版、同一项目的仓库与教程）常产出大量语义重复论点，不去重会导致同一
   论点被反复验证、同一文档被重复拉取。去重结果写入 `dedup-claims.json`。
   判重标准要保守：claim 的主语与关键对象（机制名/API 名/数字结论）一致才算重复；仅主题
   相似但细节不同的论点不要强行合并（如同一库的不同版本号、不同口径的数字，合并会掩盖
   矛盾，这类应留给 Verifier 交叉核对）。
3. **按 sources 个数递减排序，取 Top 20**：sources 越多说明被越多独立来源记载，优先验
   证。Top 20 之外被裁剪的论点在报告「待进一步研究的论点」部分列出条数即可，不逐条展开。
4. **派发 Verifier（两种粒度可选）**，所有 Verifier 的 Task 调用放在同一条回复里一次性发
   出，并发执行。Verifier 的 prompt 按 `references/verifier_prompt.md` 模板填写，模板内
   含从严的 confidence 判定标准；Verifier 同样按来源 URL 在当前可用工具中选择抓取方式：
   - **默认单论点派发**：传递总问题、该论点（claim）、其 sources（并集后的全部）、其输
     出文件路径（`<会话目录>/verifier-<n>.json`）。
   - **按主源分批派发**：多个论点引用同一主源文档时，可把同主源的整批论点交给一个
     Verifier（一次拉取文档核验整批），省 token 且同源论点间的矛盾能一并暴露。
   `corroborated_by` > 1 的论点可在 prompt 中注明「该论点由 N 个独立来源一致记载」，作
   为多源印证的参考线索——但 Verifier 仍须逐源核实，多源记载也可能集体转抄同一错误源
   头。
   **confidence 判定从严**（详见模板）：high 必须有第二独立来源交叉印证或来源内部结构性
   自洽证据；仅能重读单一来源、原文确实如此记载的，**上限 medium**——重读来源本身记载
   正确不构成 high。
5. 收集：每个 Verifier 只返回其输出文件路径。全部完成后，主 agent 读所有
   `verifier-<n>.json`，机械合并（含 low）写入 `verifier.json`，不在本步筛选。

### 第 5 步：合并排序，输出报告

主 agent 完成收尾（无需再派子代理）：

1. 读 `verifier.json`，**剔除 confidence=low 的论点**。
2. **残余去重**：第 4 步已在 Verifier 前做过一轮语义合并，本步只需合并验证阶段新暴露的
   重复（不同 Verifier 对相近论点给出互补 evidence 时，合并为一条，sources 取并集，
   confidence 取较高者）。
3. 按 confidence 从高到低排序（high → medium → low），同一置信度内按逻辑主题归组。
4. **用 Read 工具读 `references/report_template.md`，按模板组织报告**（固定五部分：总
   结 / 论点详述 / 论点多角度对比 / 待进一步研究的论点 / 参考来源；论点小节须三要素
   齐全，案例必须来自该论点的 evidence/sources，每个引用链接必须确实支撑对应论断——
   详见模板内的填写约束）。模板不常驻上下文，用前再读，以减少主 agent 上下文占用。
5. 把报告写入 `<会话目录>/report.md`，然后完整输出给用户。

## 硬性规则

1. **子代理一律只回文件路径**：Searcher / Fetcher / Verifier 的产出写入各自文件后，只返
   回文件路径，不回传文件内容——大段文本在主上下文反复传递是最大的 token 浪费源。
2. **URL 必须真实**：Searcher 只输出搜索结果里实际存在的 URL，禁止凭记忆编造链接。
3. **论点必须可证伪**：Fetcher 提取的是具体、可被证据证实或推翻的论断（含关键数字/结
   论），不是泛泛背景。
4. **验证以反证优先**：Verifier 主动找反证，而不是寻找支持论点的证据；低置信度一律剔除。
5. **引用必须真实**：报告中每个引用链接的来源必须确实支撑对应论断。
6. **单点失败不阻塞**：某个 Searcher / Fetcher / Verifier 失败或超时，跳过并在报告「待
   进一步研究的论点」部分说明。
7. **去重先于验证**：论点语义去重必须在派发 Verifier 之前完成（第 4 步第 2 点），禁止
   带着重复论点进入验证阶段；被裁剪出 Top 20 的论点须在「待进一步研究的论点」部分交代。
8. **来源分层与裁剪透明**：内部来源/权威来源优先于公网/二手来源（第 3 步排序规则 a），
   但权威性只影响入选优先级，不影响后续验证强度——任何来源的论点都必须经过 Verifier
   对抗验证；所有被配额或同簇规则裁剪的 URL/论点须在「待进一步研究的论点」部分交代。
