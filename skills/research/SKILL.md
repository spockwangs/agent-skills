# Research

用子 Agent 去**找答案**，让找答案过程中的副产品（文件全文、日志噪声、死胡同）进不到你自己的上下文。你拿回蒸馏后的答案和支撑证据，把注意力留给真正要做的事。

本技能只做仓库内调查（读代码、日志、diff）。开放式多源调研走 `deep-search`。无论走哪条路径，证据规则相同：**只采信一手来源。**

## 一手来源

每条主张都追到**拥有该事实的源头**：实现它的源码、发出它的官方文档/规范/第一方 API、产生它的原始日志或 diff。博客、二次整理、转述、汇总、README 里的复述是路标，不是终点——沿它的引用、链接、commit、issue 继续查，直到读到一手。

完成标准：报告里每条可核对的结论都挂在一手来源上（路径 + 符号/段落）。只找到二手时写明「未追到一手」以及停在哪，把二手当路标而不是证据。

## 何时用

当**产出答案的成本远大于答案本身**时派发。强信号：

- 要读很多文件才能找到少数相关的
- 要在长测试输出、CI 日志或堆栈里抽出一次失败
- 要普查某个模式、API 或符号在全仓库的用法
- 要读并总结一份大 diff 或 PR
- 问题有若干彼此独立、可分开查的子部分

**适合：**

- 「这个失败测试的根因是什么？」（子 Agent 读日志、追代码；你拿到原因）
- 「`SessionManager` 在代码库里怎么被用？」（子 Agent grep 再读；你拿到带调用点的摘要）
- 「这份 4000 行 PR 改了什么、为什么？」（子 Agent 读 diff；你拿到形状）

**自己做：**

- 已经知道要读的 2–3 个文件：直接读，派发只加延迟
- 一次 `grep` 或一行查找：自己做
- **下一步就要直接改这些文件。** 派发完还得自己再读一遍才能改。调研派发赚的是**结论**，不是你马上要动手的原材料。

子 Agent 有真实成本（延迟和 token）。判断标准始终是：避开的噪声是否超过这笔成本。

## 怎么做

### 本地、搜索向模型

调研子 Agent **一律本地**，不要 remote / cloud——即使父 Agent 自己是 factory 或 cloud。

模型按搜索任务选，不跟父 Agent。子 Agent 的工作是搜索和蒸馏，不是分析：简单查找用更快更便宜的搜索档；要顺着调用点追数据流时再用更强一档。Cursor 下：`subagent_type` 普查用 `explore`，更深的追踪用 `generalPurpose`；`environment` 为 `local`。

### 单个 vs 并行

默认 **一个**子 Agent。问题真正拆成彼此独立、不必共享中间发现的子部分时，才 **并行多个**——例如「鉴权怎么工作 AND 计费怎么工作 AND 限流怎么工作」是三次独立调查，可以同时跑。部分真正独立时并行值得用；不要把一个连贯问题硬拆成碎片。

### 简报要写全

子 Agent 不共享你的意图，必须写清楚。一份好的调研简报包括：

- 要回答的精确问题
- 去哪找（仓库路径、分支、已知的可疑文件/符号）
- **只读**：调查并汇报，不改文件，除非任务明确要求改
- **一手来源**：每条主张追到拥有该事实的源头；二手只作路标，沿引用继续查
- 你要拿回的产出（见下）
- **不要**再调用 `/research` 或再派子 Agent：本次调查直接做

### 要信号，不要逐字稿

让子 Agent 返回 **蒸馏答案 + 支撑证据**，不要原文倾倒。具体要：

1. 对问题的直接回答
2. 关键证据：每条结论对应的**一手**出处——精确文件路径和符号（如 `src/session.rs:142`、`fn reconnect`），或官方文档/规范的具体段落。二手出处最多当作「由此追到的路径」
3. 任何意外发现，以及碰到的 caveat / 未知（含「未追到一手」）

噪声留在子 Agent 那边。报告若臃肿，对**同一个**子 Agent 发一条收紧的 follow-up——它保留上下文，收紧更便宜。

完成标准：你拿到可核对的答案（结论 + 挂在一手来源上的证据 + 未知点），且自己的上下文里没有那堆原始文件/日志。

## 拿到答案之后

从蒸馏结果继续工作。若后来发现改代码需要底层文件，那时再直接读——现在你已经知道哪几个要紧，读三份而不是二十份。
