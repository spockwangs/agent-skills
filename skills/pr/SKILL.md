# 提交 PR

目标：提交后由独立子 agent 跟进到合并完成。

## 1. 创建分支并提交

1. 查看 `git status`、待提交 diff 和近期提交格式。不得提交无关文件、密钥或本地 `.claude` 目录。
2. 如果当前分支是 `master`，创建语义清晰的 feature 分支；否则使用当前分支。
3. 只暂存本次 PR 相关文件。
4. 生成准确描述改动目的的 commit message，提交并 push source branch。不得跳过 hooks，不得 force push。

若用户要求把某个服务或目录拆成独立 PR，使用独立 worktree 从最新 `origin/master` 创建分支，只带入指定改动，避免切换分支时影响当前工作区。

## 2. 创建 pull request

1. 用仓库所在平台的 pull request 命令创建 PR。GitHub 上使用 `gh pr create`。描述必须包含：

```markdown
## 【代码改动】
<改动及原因>

## 【测试方法】
<实际执行的编译和测试命令及结果>
```

2. 正文使用真实换行，不使用字面量 `\n`。
3. 记录 PR 链接以及后续轮询必需的：
   - PR 编号；
   - `source_branch`；
   - 当前最新评论时间，作为评论游标。

## 3. 启动子 agent 跟进 PR 直到合并

创建 PR 后立即启动另一个可长时间运行、可修改代码的子 agent；支持后台运行时使用后台模式，优先给它独立 worktree。把仓库路径、PR 链接、PR 编号、`source_branch`、评论游标和以下闭环任务完整传给它。

### 3.1 轮询

- 每约 13 分钟检查一次；若环境提供会话级定时或唤醒能力，优先使用它，否则在子 agent 的单次 run 内等待后继续。
- 每轮只检查一次。没有新状态时保持等待，不重复催促评审人。
- 持续运行，直到 PR 已合并、已关闭或满足“异常停止”条件。

### 3.2 每轮处理

1. 查询 PR：
   - 仍打开：继续处理评论与检查；
   - 已合并：执行收尾并报告 PR 链接；
   - 已关闭且未合并：停止并报告。
2. 查询比评论游标更新的评论，随后推进游标。
3. 忽略：
   - 已解决的评论；
   - 普通系统消息和 CI 报告；
   - 机器人评论；
   - 以 `<table` 开头的质量报告。
4. 评审人提交的通过记录，记为该评审人已通过。
5. 对新的有效评审意见：
   - 先判断意见是否成立；不成立时礼貌说明依据；
   - 需要改代码时，做最小修复，并检查同类逻辑、相关日志和测试；
   - 重新编译并运行相关单元测试，失败则继续修复；
   - 回复对应评论，说明修复内容、验证结果和 commit SHA，并将其标记为已解决；
   - 处理完一批评论后，发一条汇总并 @ 必要评审人重新 review。
6. 仅需解释的评论，回复说明并在确认解决后标记为已解决。

### 3.3 合并与停止条件

PR 合并就绪需同时满足：

- 没有合并冲突；
- 必需的检查已通过，且没有阻断合并的失败检查；
- 必要评审人已通过。

若已就绪但未自动合并，只报告并询问用户是否手动触发合并；未经明确授权不得调用合并操作。

以下情况停止子 agent 并请求人工介入：

- PR 被关闭但未合并；
- 连续至少 3 轮出现无法收敛的新意见；
- 编译或单元测试失败且无法可靠修复；
- 权限、认证、冲突或基础设施问题阻止继续。

合并后清理本流程创建的临时 worktree 或会话级定时任务，保留 source branch，向用户报告 PR 链接和最终状态。
