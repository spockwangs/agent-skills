从一个 issue（链接或编号）判断「这是不是真问题、卡在哪、下一步该做什么」。验证只做到能定性：needs-triage, needs-info,
wontfix, ready。深挖根因交给用户显式要求，或后续用诊断类流程。

读取 issue 的方式遵循当前用户或项目的 `AGENTS.md`。一次只诊断一个 issue。

诊断与 issue tracker 写入分成两拍：先把结论发给用户并停下来等确认；用户确认后再写评论、改 label、关 issue。所有评论都在
前面加上如下一句免责声明：

```
> Generated by AI.
```

## 类别和状态

每个issue有两个类别：
- bug: 系统不能正常工作
- 优化：新功能或改进

有如下几个状态：
- `needs-triage`: 需要开发评估
- `needs-info`: 需要报告者提供更多信息
- `ready`: 需求和方案已明确，可以开发了
- `denied`: 评估后拒绝了，要么bug未复现，要么没实现的价值
- `resolved`: 功能已实现或bug已修复

## 步骤

1. **获取上下文：** 读 issue 正文、labels、作者、状态和全部评论。已被拒绝或在评论里解决过的问题不要再问。

2. **对照代码：** 读仓库 `CONTEXT.md` / ADR（若有）。按**领域概念**搜，不只搜 reporter 的原词：
   - **冗余**：请求的行为是否已经存在。写明搜了哪些概念、落在哪。如果找到了，结论就是“已实现”。
   - **相关路径**：当前行为实际走哪条代码/接口/配置。

3. **验证主张：** 在提问之前先验证。
    - **bug**：按 reporter 的步骤复现。报告三者之一：已确认（带代码路径）、无法复现、步骤不够（强「信息不足」信号）。
   - **enhancement / 需求**：对照现状，判断是缺口、已实现，还是理解偏差。
   - 几分钟内复现不了就停，不要展开成长诊断。把尝试过的步骤写进结论。

4. **继续分析（如果需要）：**如果问题过于复杂，还有细节需要理清，调用技能`analysis`详细询问。

5. **把诊断结论发给用户并停下来。** 本步完成条件：用户已经看到结论并回复确认或要求改。回复里写清：类别（bug / 优化）、建议状态、拟写的评论全文、是否关 issue。用户要求改结论时，改完再停一次。此步只读 issue tracker。

6. **用户确认后再写 issue tracker**（按确认后的结论）：
   - 已实现：发布一条评论解释在哪里实现了，标记为`resolved`并关闭这条issue。
   - bug无法复现：发布一条评论解释为什么复现不了，标记为`denied`并关闭这条issue。
   - 特性被拒绝：发布一条评论解释原因，标记为`denied`并关闭这条issue。
   - 需要更多信息：发布一条评论（模版参考[needs-info.md](references/needs-info.md)），标记为`needs-info`。
   - 需要进一步诊断：发布一条评论解释当前进展，标记为`needs-triage`.
   - 已明确，待实现：发布一条评论（模版参考[agent-brief.md](references/agent-brief.md)），标记为`ready`.
