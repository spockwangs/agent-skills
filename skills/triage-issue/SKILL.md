Given one issue (link or number), decide: is this a real problem, where is it stuck, and what should happen next. Verify only
as far as needed to assign a status: `needs-triage`, `needs-info`, `denied`, or `ready`. Leave deep root-cause analysis to an
explicit user request or a follow-up diagnosis workflow.

Read the issue the way the current user's or project's `AGENTS.md` specifies. Triage one issue at a time.

Diagnosis and issue tracker writes happen in two beats: first send the verdict to the user and stop to wait for confirmation;
only after the user confirms, post comments, change labels, or close the issue. Prefix every comment with this disclaimer:

```
> Generated by AI.
```

## Categories and statuses

Every issue falls into one of two categories:
- `bug`: the system does not work correctly
- `enhancement`: a new feature or an improvement

Statuses:
- `needs-triage`: needs evaluation by a developer
- `needs-info`: needs more information from the reporter
- `ready`: requirements and approach are clear; ready to implement
- `denied`: rejected after evaluation, either the bug did not reproduce or the feature is not worth building
- `resolved`: the feature is implemented or the bug is fixed

## Steps

1. **Gather context:** Read the issue body, labels, author, status, and all comments. Do not re-ask questions that were already
   rejected or answered in the comments.

2. **Check against the code:** Read the repo's `CONTEXT.md` / ADRs (if any). Search by **domain concept**, not only by the
   reporter's exact words:
   - **Redundancy**: does the requested behavior already exist? Record which concepts you searched and where they landed. If you
     find it, the verdict is "already implemented".
   - **Relevant path**: which code path, API, or config the current behavior actually goes through.

3. **Verify the claim:** Verify before asking questions.
   - **bug**: Reproduce using the reporter's steps. Report one of three outcomes: confirmed (with the code path), cannot
     reproduce, or steps insufficient (a strong "needs info" signal).
   - **enhancement**: Compare against current behavior and decide whether it is a real gap, already implemented, or a
     misunderstanding.
   - If you cannot reproduce within a few minutes, stop; do not expand into a long diagnosis. Include the steps you tried in the
     verdict.

4. **Clarify with the user (if needed):** If the issue is complex or ambiguous and details still need to be pinned down before
   a verdict is possible, call the skill tool with `grill` to interview the user until the open decisions are settled. Then continue
   with the next step.

5. **Send the verdict to the user and stop.** Write the verdict to some path outside the repo and present the path (*not
   the content*) to the user. This step is done when the user has seen the verdict and replied to confirm or asked for
   changes. The reply must state: category (`bug` / `enhancement`), proposed status, the full text of the comment to
   post, and whether to close the issue. If the user asks for changes, revise and stop again. This step only reads the
   issue tracker.

6. **Write to the issue tracker after confirmation** (per the confirmed verdict):
   - Already implemented: post a comment explaining where it is implemented, mark it `resolved`, and close the issue.
   - Bug cannot be reproduced: post a comment explaining why it could not be reproduced, mark it `denied`, and close the issue.
   - Feature rejected: post a comment explaining why, mark it `denied`, and close the issue.
   - Needs more info: post a comment (template: [needs-info.md](references/needs-info.md)) and mark it `needs-info`.
   - Needs further diagnosis: post a comment describing current progress and mark it `needs-triage`.
   - Clear and ready to implement: post a comment (template: [agent-brief.md](references/agent-brief.md)) and mark it `ready`.
